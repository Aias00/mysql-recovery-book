# 附录C：术语与快速核对表

| 术语 | 本书中的准确含义 |
| --- | --- |
| 一致快照 | 事务表在同一逻辑视图下读取，不等于导出结束时最新数据 |
| 逻辑备份 | 用SQL等逻辑表达保存结构与数据，恢复时重新执行 |
| 基线 | 后续日志回放的已验证起始数据状态 |
| binlog | MySQL服务器层变化日志，用于复制与目标恢复 |
| redo | InnoDB内部崩溃恢复所用日志，不是mysql客户端回放输入 |
| PITR | 在基线之后按日志恢复到明确目标边界 |
| GTID | 事务身份及其集合表达，不是业务正确性证书 |
| relay log | 副本接收后供应用线程执行的中继日志 |
| 接收水位 | 副本已经取得的日志进度，不等于业务可见进度 |
| 执行水位 | 副本已应用的事务进度，仍需检查数据内容 |
| fence | 在提升新主前排除旧主继续写入的实际边界 |
| super_read_only | 服务器只读限制，管理员可改变，不能替代全部外部隔离 |
| RPO | 允许或实际发生的数据损失范围，需说明业务单位与边界 |
| RTO | 从明确故障起点到明确服务终点的时间，需列出包含阶段 |
| 分叉 | 两个节点分别接受写入，形成不同事务与业务未来 |
| 归档摘要 | 标识文件字节的SHA-256，不单独证明日志连续与业务正确 |

恢复前先问：输入是否独立可得，范围是否连续，目标是否隔离？回放时先问：坐标是否来自真实基线，结束是否为完整事务边界？提升时先问：旧主是否已被实际阻断，候选节点缺什么？验收时先问：哪些确认交易保留，哪些事务排除，不变量是否成立？收尾时先问：分叉证据是否保存，新主的备份与归档是否已经接续？
